# I2C / SMBus on x86 architecture research  
  
## Motivation  
  
I2C bus is super simple - most basic bus and foundation for digital communication, like DDC in HDMI, SPD in computer memory modules,  SMBUS in “Smart battery”, PMBUS for power management, image sensors configuration in CSI cameras, and so on and on.   
  
Talking to those devices on a MCU in C language is simple - often limited to communication with peripheral for sending and receiving data. But it gets more complicated on x86 architecture, which can be found in many computer systems (aka personal computers and laptops). Simple Cortex M0 core running at 100MHz is “just” one thousand faster than the slowest 100kbps I2C bus speed. But on average modern CPU running at 3GHz it is 30 thousand times faster. There is no surprise that CPU is not talking to I2C peripherals directly as probably it is waste of interrupts - as changing context on CPUs this complex is really wasteful for pipeline processing.   
  
As already found that many of small sensors like temperature, fan controllers, additional buttons aka “hot heys”, orientation sensors or even touchpads works on I2C or some variation of it like SMBUS. And was just curious how to communicate with them from the operating system. And of course all those reflections are related to future x86 project.   
  
## Approach  
  
Build simple prototype board with a few sensors working on I2C / SMBUS bus connect it to a x86 motherboard with exposed I2C signals and try to access them from the operating system.   
  
## Goals:  
  
Goals for this quick research are low - start small and achieve some basic functionality:  
  
- Communicate with some sensors on linux using i2c tools  
- Bind already build driver to a device on linux  
- Communicate with sensors on Windows 11  
  
## Understanding I2c handling on x86 architecture   
  
On an x86 SoC, I2C transfers are generated by dedicated I2C controller hardware, similar in principle to MCU I2C peripherals, but the controller is integrated into a much larger platform with firmware, pin muxing, power management, and OS enumeration around it. First, firmware configures the pads so the selected pins work as SDA/SCL instead of GPIO or another alternate function, then it enables or describes the I2C controller and any fixed devices connected to that bus. When software requests a transaction, the CPU does not bit-bang the bus; it programs controller registers or uses DMA/FIFO mechanisms, and the controller generates START, address, ACK/NACK, data bytes, repeated START, STOP, and clock timing. The important difference from a small MCU is not the existence of an I2C peripheral, but the amount of platform infrastructure around it: ACPI/firmware tables, controller drivers, device drivers, interrupts, runtime power states, and security/ownership rules. Later in the OS stack, the I2C controller becomes a bus adapter, devices on that bus become child devices, and normal applications usually access the sensor through a driver-specific or framework-specific interface rather than by directly controlling bus transactions.

## Components selection for the research  
  
For the component selection, I tried to find parts that are commonly mounted on x86-based motherboards and have proven Windows support. For the temperature sensors, I found that TMP101 and TMP175 are widely used as internal temperature sensors. For fan-speed readings, I selected the MAX6650EUB+. For the IMU/gyroscope, I chose the Bosch BNO055, the MPU-6050, and the ST LSM6DSOTR. For the GPIO expander, the choice was more arbitrary, as I could not find clear listings of specific chips used in laptops. Usually, this functionality is hidden behind a driver package for a particular laptop model, often described only as “hot keys support”.

## Software test setup - Linux  
   
  
Picked most layman friendly Linux - Lubuntu 26.04  
It is equipped with apt for easy software install, comes with thousands of drivers, easy for install - seems to be good choice for a quick start.  
It runs of a usb drive as a live ISO.  
When installing or running from usb drive I believe no one ponder “from where did it know all the hardware on the motherboard?”. It just works and no one cares. But actually it is quite interesting. On most ARM platforms Linux kernel expects so called device tree binary (.dtb file) - describing all peripherals and their addresses in the memory. On x86 this information is stored in the firmware (BIOS/UEFI) in a form so called ACPI tables. This approach makes OS installation much easier as the firmware already contains information about the hardware and supplying device tree externally is not required. Linux reads it and loads required drivers. For already described modules like touch screen controller or internal temperature sensors they will “automagically” start to work. For external devices, such as a custom board with I²C sensors, Linux provides a convenient way to experiment without modifying low-level firmware, which could easily make the device harder to recover. The `i2c-tools` package uses the Linux I²C userspace interface exposed through `/dev/i2c-*`, typically provided by the `i2c-dev` kernel module. This makes direct bus testing much easier during bring-up.

### Communication with temperature sensor STTS22HTR  
  
For starters read WHOAMI register, which according to a datasheet should be 0x0A  
```bash  
lubuntu@lubuntu:~$ sudo i2cget -y 4 0x38 0x01                  
0xa0  
```  
  
Read basic registers:  
  
```bash  
# CTRL register  
lubuntu@lubuntu:~$ sudo i2cget -y 4 0x38 0x04
0x30  
  
# STATUS register  
lubuntu@lubuntu:~$ sudo i2cget -y 4 0x38 0x05              
0x00  
  
# Temperature low byte  
lubuntu@lubuntu:~$ sudo i2cget -y 4 0x38 0x06
0x00  
  
# Temperature high byte  
lubuntu@lubuntu:~$ sudo i2cget -y 4 0x38 0x07
0x00  
```  
Temperature registers return zeros - expected as sensor was not yet asked to take a measurement.   
  
```bash  
# Start one-shot conversion  
lubuntu@lubuntu:~$ sudo i2cset -y 4 0x38 0x04 0x01
  
# Read high and low temperature bytes once again  
lubuntu@lubuntu:~$ sudo i2cget -y 4 0x38 0x06              
0x32  
lubuntu@lubuntu:~$ sudo i2cget -y 4 0x38 0x07         
0x0a          
```  
  
Command for reading register values and formatting them in a human readable form:  
```bash  
lubuntu@lubuntu:~$  sudo i2cset -y 4 0x38 0x04 0x01; sleep 0.1; lo=$(sudo i2cget -y 4 0x38 0x06); hi=$(sudo i2cget -y 4 0x38 0x07); raw=$(( (hi << 8) | lo )); if [ $raw -ge 32768 ]; then raw=$((raw - 65536)); fi; awk "BEGIN { printf \"Temperature: %.2f C\n\", $raw / 100 }"  
Temperature: 26.10 C  
```  
Which in a room, close to the running CPU seems to be accurate.  
  
  
### Communication with GPIO expander TCA9536DGKR  
  
  
Based on the schematic:  
```text  
P0 = input  
P1 = input  
P2 = output  
P3 = output  
```  
  
Based on documentation - TCA9536 registers:  
```text  
0x00 - Input port  
0x01 - Output port  
0x02 - Polarity inversion  
0x03 - Configuration  
       bit = 1 means input  
       bit = 0 means output  
```  
  
Configure P0/P1 as inputs, P2/P3 as outputs:  
```bash  
# binary: 00000011  
# P0=input, P1=input, P2=output, P3=output  
sudo i2cset -y 4 0x41 0x03 0x03  
```  
  
Read P0/P1 input states (both not pressed):  
```bash  
sudo i2cget -y 4 0x41 0x00
0xff  
```  
  
Copy-paste readable version (P0 pressed):  
```bash  
v=$(sudo i2cget -y 4 0x41 0x00)  
echo "Raw input: $v"  
echo "P0 = $(( v & 1 ))"  
echo "P1 = $(( (v >> 1) & 1 ))"  
Raw input: 0xf2
P0 = 0
P1 = 1
```  
  
Set P2 high, P3 high (LEDs should lit):  
```bash  
sudo i2cset -y 4 0x41 0x01 0x0C  
```  

Set P2 low, P3 low (LEDs should turn off):  
```bash  
sudo i2cset -y 4 0x41 0x01 0x00  
```  
  
### Communication with 6-axis IMU ST LSM6DSOTR  
  
Important registers:  
```text  
0x0F - WHO_AM_I, expected 0x6C  
0x10 - CTRL1_XL, accelerometer config  
0x11 - CTRL2_G, gyroscope config  
0x20 - OUT_TEMP_L  
0x22 - OUTX_L_G  
0x28 - OUTX_L_A  
```  
  
  
Check device ID:  
```bash  
sudo i2cget -y 4 0x6a 0x0f  
```  
Expected:  
```text  
0x6c  
```  
  
Enable accelerometer and gyroscope:  
```bash  
# Accelerometer: 104 Hz, +/-2g  
sudo i2cset -y 4 0x6a 0x10 0x40  
  
# Gyroscope: 104 Hz, +/-250 dps  
sudo i2cset -y 4 0x6a 0x11 0x40  
```

Manually instantiate the I²C device via sysfs so the kernel knows that an lsm6dso sensor exists at address 0x6a on I²C bus 4. Normally this information comes from ACPI or Device Tree, but new_device provides a simple runtime way to register the device with the OS.

```bash
lubuntu@lubuntu:~$ echo lsm6dso 0x6a | sudo tee /sys/bus/i2c/devices/i2c-4/new_device               
lsm6dso 0x6a  
```
  

After manually instantiating the device, i2cdetect run to verify the state of I²C bus 4. The UU entry at address 0x6a indicates that the address is occupied and currently claimed by a kernel driver, which confirms that the manually added lsm6dso device was registered and bound by the kernel.

## 3rd goal - communication with a device on ~~Windows 11~~ Lubuntu 26.04 using ACPI

The initial goal was to add one custom I²C device on Windows 11. Since the sensor is connected to an internal I²C bus on an x86 machine, the proper way to describe the hardware to the operating system is through ACPI.

In theory, this should be similar to embedded Linux Device Tree overlays: describe the device, expose it to the OS, bind a driver, and use it from userspace.

In practice, doing this on Windows requires entering the Microsoft driver development universe: ACPI tables, INF files, driver signing, WDK tooling, and a much less friendly development/debug loop. After spending some time researching that path, I decided to switch to Lubuntu 26.04 for development.

The new plan was:

1. Use Lubuntu 26.04 as the development OS.
2. Add the IMU to the system using an ACPI SSDT overlay.
3. Bind the existing Linux kernel driver to the ACPI-enumerated I²C device.
4. Confirm that the IMU appears as normal Linux IIO devices.
5. Use accelerometer data to rotate the screen.

This still closely reflects the Windows approach, because the important part is the same: the device is no longer manually instantiated through sysfs. Instead, it is described in ACPI, just like a firmware-provided device would be.

### Why ACPI?

On embedded Linux boards, custom hardware is often described with Device Tree. On x86 computers, the equivalent hardware-description mechanism is ACPI.

Without ACPI, the IMU can still be tested manually, as shown in previous chapters, using `i2cget`, `i2cset`, or by creating a temporary I²C device through:

```bash
echo lsm6dso 0x6a | sudo tee /sys/bus/i2c/devices/i2c-4/new_device
```

This is useful for testing, but it is not how a real system should expose hardware.

A proper system-level integration should tell the OS:

* which I²C controller the device is connected to,
* what I²C address it uses,
* what compatible device type it is,
* and which kernel driver should bind to it.

On this machine, the IMU is connected to Linux I²C bus 4 at address `0x6a`. However, ACPI does not use Linux bus names such as `i2c-4`. ACPI uses firmware namespace paths.

The first step was therefore to find the ACPI path behind Linux `i2c-4`.

### Finding the ACPI path of I²C bus 4

The Linux I²C bus was already known:

```bash
i2c-4
```

The ACPI firmware node for this bus can be found through sysfs:

```bash
readlink -f /sys/bus/i2c/devices/i2c-4/firmware_node
```

On this system it returned:

```text
/sys/devices/LNXSYSTM:00/LNXSYBUS:00/PNP0A08:00/device:69
```

This is not yet the ACPI namespace path. It is the Linux sysfs path to the ACPI firmware node.

The real ACPI path can be read from the `path` file:

```bash
cat /sys/bus/i2c/devices/i2c-4/firmware_node/path
```

Result:

```text
\_SB_.PC00.I2C5
```

So even though Linux calls the bus `i2c-4`, the ACPI controller path is:

```text
\_SB_.PC00.I2C5
```

This mismatch is normal. The ACPI SSDT must use the ACPI path, not the Linux bus number.

### Creating an ACPI SSDT overlay

The goal is to describe the ST LSM6DSO IMU as a child device of the I²C controller `\_SB_.PC00.I2C5`.

Important values:

```text
I²C controller ACPI path: \_SB_.PC00.I2C5
I²C address:              0x6a
Sensor:                   ST LSM6DSO / LSM6DSOTR
Linux driver:             st_lsm6dsx_i2c
Compatible string:        st,lsm6dso
```

Create a working directory:

```bash
mkdir -p ~/acpi-lsm6dso
cd ~/acpi-lsm6dso
nano ssdt-lsm6dso.asl
```

Create the following ASL file. ASL stands for ACPI Source Language and it is written in human readable form. In this file we create a small SSDT overlay that adds the LSM6DSO as a child device of the existing I²C controller `\_SB_.PC00.I2C5`, describes its I²C address `0x6a`, and provides the `st,lsm6dso` compatible string so Linux can bind the `st_lsm6dsx_i2c` driver.

```asl
DefinitionBlock ("", "SSDT", 2, "USER", "LSM6DSO", 0x00000001)
{
    External (\_SB_.PC00.I2C5, DeviceObj)

    Scope (\_SB_.PC00.I2C5)
    {
        Device (IMU0)
        {
            Name (_HID, "PRP0001")
            Name (_DDN, "STMicroelectronics LSM6DSO 6-axis IMU")

            Name (_CRS, ResourceTemplate ()
            {
                I2cSerialBusV2 (
                    0x6A,
                    ControllerInitiated,
                    400000,
                    AddressingMode7Bit,
                    "\\_SB_.PC00.I2C5",
                    0x00,
                    ResourceConsumer,
                    ,
                    Exclusive
                )
            })

            Name (_DSD, Package ()
            {
                ToUUID ("daffd814-6eba-4d8c-8a91-bc9bbf4aa301"),
                Package ()
                {
                    Package () { "compatible", "st,lsm6dso" }
                }
            })
        }
    }
}
```

Let's break it into pieces:

```asl
DefinitionBlock ("", "SSDT", 2, "USER", "LSM6DSO", 0x00000001)
```

This defines a new ACPI table. `SSDT` means **Secondary System Description Table**, which is an additional ACPI table loaded alongside the firmware-provided tables. `USER` is the OEM ID, `LSM6DSO` is the table ID, and `0x00000001` is the table revision.

```asl
External (\_SB_.PC00.I2C5, DeviceObj)
```

This tells the ASL compiler that `\_SB_.PC00.I2C5` already exists in another ACPI table. In this case, it is the existing firmware-defined I²C controller that Linux exposes as `i2c-4`.

```asl
Scope (\_SB_.PC00.I2C5)
```

This opens the namespace of that existing I²C controller. Everything inside this block is added below `\_SB_.PC00.I2C5`.

```asl
Device (IMU0)
```

This creates a new ACPI device named `IMU0` under the I²C controller. The name is local to ACPI and can be any valid four-character ACPI name.

```asl
Name (_HID, "PRP0001")
```

`_HID` is the ACPI Hardware ID. `PRP0001` is used when Linux should match the device using the Device Tree-style `compatible` property from `_DSD`.

```asl
Name (_DDN, "STMicroelectronics LSM6DSO 6-axis IMU")
```

`_DDN` is a human-readable device description. It is useful for debugging and documentation, but it is not the main driver-matching mechanism.

```asl
Name (_CRS, ResourceTemplate ()
```

`_CRS` means **Current Resource Settings**. This section describes the hardware resources used by the device. For this IMU, the important resource is the I²C connection.

```asl
I2cSerialBusV2 (
    0x6A,
    ControllerInitiated,
    400000,
    AddressingMode7Bit,
    "\\_SB_.PC00.I2C5",
    0x00,
    ResourceConsumer,
    ,
    Exclusive
)
```

This describes the I²C bus connection. `0x6A` is the 7-bit I²C address of the LSM6DSO. `400000` is the bus speed, 400 kHz. `AddressingMode7Bit` means the device uses a normal 7-bit I²C address. `"\\_SB_.PC00.I2C5"` points back to the parent I²C controller. `ResourceConsumer` means the IMU consumes this bus resource. `Exclusive` means this I²C address/resource is intended for this device only.

```asl
Name (_DSD, Package ()
```

`_DSD` means **Device Specific Data**. Linux uses this section to read extra device properties that are not represented by standard ACPI fields.

```asl
ToUUID ("daffd814-6eba-4d8c-8a91-bc9bbf4aa301")
```

This UUID identifies the standard ACPI device-properties format. It tells Linux that the following package contains key/value properties such as `compatible`.

```asl
Package () { "compatible", "st,lsm6dso" }
```

This is the key driver-matching property. It tells Linux that this ACPI device is compatible with `st,lsm6dso`. The `st_lsm6dsx_i2c` driver has a matching alias for this compatible string, so the kernel can bind the IMU to that driver.

### Using the accelerometer for screen rotation


On Linux tablets and convertibles, the usual path is:

```text
accelerometer hardware
    ↓
kernel sensor driver
    ↓
IIO subsystem
    ↓
iio-sensor-proxy
    ↓
desktop environment
    ↓
screen rotation
```

The kernel driver exposes the accelerometer through the Linux IIO subsystem, usually under `/sys/bus/iio/devices/`. A userspace daemon called `iio-sensor-proxy` reads the accelerometer data, converts it into orientation states such as `normal`, `left-up`, `right-up`, or `bottom-up`, and exposes that information over D-Bus. Desktop environments such as GNOME and KDE/Plasma can then use that orientation information to rotate the display automatically.

In this project, the LSM6DSO follows the same general Linux model. After the ACPI SSDT creates the I²C device and the `st_lsm6dsx_i2c` driver binds to it, Linux exposes two IIO devices: one for the gyroscope and one for the accelerometer. The accelerometer device is the one needed for screen rotation.

On a full tablet-oriented desktop stack, `iio-sensor-proxy` may handle the orientation automatically. In this Lubuntu/X11 setup, the same idea can also be implemented manually: read the accelerometer X/Y values from IIO, decide the current orientation, and call `xrandr` to rotate the screen.


Although the chip also contains a gyroscope, screen rotation should use the accelerometer. The accelerometer measures the gravity vector, so it can tell which side of the device is currently pointing down.

First, install display and sensor helper tools:

```bash
sudo apt install -y iio-sensor-proxy x11-xserver-utils
```

Check the connected display name:

```bash
xrandr --query
```

Example output:

```text
HDMI-1 connected
```

Test manual rotation:

```bash
xrandr --output HDMI-1 --rotate left
xrandr --output HDMI-1 --rotate normal
xrandr --output HDMI-1 --rotate right
xrandr --output HDMI-1 --rotate inverted
```

If manual rotation works, the next step is to use the accelerometer values to choose the correct orientation.

A simple direct-IIO rotation script can read the accelerometer raw X and Y values and rotate the screen based on the dominant axis:

```bash
#!/usr/bin/env bash

DISPLAY_OUT="HDMI-1"

ACCEL_DEV=$(grep -l "lsm6dso_accel" /sys/bus/iio/devices/iio:device*/name | sed 's|/name||')

if [ -z "$ACCEL_DEV" ]; then
    echo "Could not find lsm6dso_accel IIO device"
    exit 1
fi

echo "Using accelerometer: $ACCEL_DEV"
echo "Using display: $DISPLAY_OUT"

last=""

while true; do
    x=$(cat "$ACCEL_DEV/in_accel_x_raw")
    y=$(cat "$ACCEL_DEV/in_accel_y_raw")

    ax=${x#-}
    ay=${y#-}

    if [ "$ay" -gt "$ax" ]; then
        if [ "$y" -gt 0 ]; then
            rot="normal"
        else
            rot="inverted"
        fi
    else
        if [ "$x" -gt 0 ]; then
            rot="right"
        else
            rot="left"
        fi
    fi

    if [ "$rot" != "$last" ]; then
        echo "Rotation: $rot   x=$x y=$y"
        xrandr --output "$DISPLAY_OUT" --rotate "$rot"
        last="$rot"
    fi

    sleep 1
done
```

Save it as:

```bash
nano ~/autorotate-iio.sh
```

Make it executable:

```bash
chmod +x ~/autorotate-iio.sh
```

Run it:

```bash
~/autorotate-iio.sh
```

Now rotating the computer should rotate the display.

    ↓

## Summary and conclusions  

The goal of this research was to check how I²C/SMBus devices can be accessed and integrated on an x86 platform.

The first goal was achieved: sensors connected to the prototype board were detected and accessed from Linux using `i2c-tools`. Temperature sensors, a GPIO expander, and an IMU were successfully read or controlled directly from userspace.

The second goal was also achieved: the existing Linux `st_lsm6dsx_i2c` driver was manually bound to the LSM6DSO IMU. After binding, the sensor was exposed through the Linux IIO subsystem as standard accelerometer and gyroscope devices.

The third goal was partially changed. Instead of continuing directly with Windows 11, the same ACPI-based integration concept was tested on Lubuntu. A custom SSDT overlay was created, compiled, and loaded at runtime. This allowed the IMU to be described through ACPI, bound automatically to the Linux kernel driver, and used from userspace for screen rotation.

Overall, the research confirmed that raw I²C communication on x86 is straightforward once the correct bus is found, but proper system integration depends on firmware description, driver binding, and OS-specific infrastructure. Linux provides a convenient path for bring-up and experimentation, while Windows integration requires further work with ACPI tables, INF files, WDK tooling, and driver signing.
